DECISIONS
=====================================================================
1. Blanket-allow interpretation: plan bans `allow: [{rule:"*"}]` shapes. A
   bare {rule:"*"} is unrepresentable in the schema (match is required), and
   suppressing this repo to exit 0 is IMPOSSIBLE with concrete rule+match
   pairs alone (497 heterogeneous findings; the sanctioned .omo/** and test/**
   categories are location-scoped). Config guard therefore rejects exactly the
   UNSCOPED pair {rule:"*",match:"*"} (zero scoping = blanket) and accepts
   wildcard pairs ONLY when file-scoped. Fail-loud default preserved
   elsewhere: empty rule/match strings, absolute/.. file globs rejected.
2. Category extensions (documented in border.yaml comments): the vendored
   gitleaks rules file (self-signatures), prompt template + src/tools
   self-matching path patterns are b-ext (the tool's own detector corpus);
   category list semantics preserved — every entry cites its category.
3. Explicit-empty no-op promotion lives in src/commands/check.ts (narrowing
   branch), NOT in loadConfig: LoadResult keeps {kind:'no-op', explicit?} so
   llm commands' "no scan targets" behavior and undiscovered-config no-op stay
   untouched.
4. allow post-filter position = after registry probes, before verdict/counts;
   registry probes cannot be allow-scoped away (they are target legs, not
   findings) — no-op config => effectiveTargets [] => probes return [] (no
   network), verified by test + dogfood.
5. report.md renders ONLY the 5 plan columns (message excluded) — this also
   makes the md an injection-minimal surface; ledger/status collapse control
   chars for the same reason.
6. Digest hole check result: allow[] IS in configDigest (verified live via
   key rotation e9f299a9 -> 06eb5c54 + unit test two-configs-differ).
